A platform team runs bare-metal log shippers, a VM web fleet, and an OpenShift cluster full of Deployments and DaemonSets — watched, as most teams' stacks are, by Grafana, Prometheus and Alertmanager. This is one night on that team's rotation, with Auto-Healer sitting between the alert and the phone.

Grafana + Prometheus + Alertmanager Bare metal & VM fleet — Ansible OpenShift — Deployments & DaemonSets

What follows is an illustrative scenario, not a real incident report — a composite of how a team could wire Auto-Healer into a stack they already run. Hostnames, timestamps and Slack handles are invented for clarity; the request payloads, config shapes and safety behavior are exactly how the system in this repository works.

Two people, one pager

Before the shift starts

The platform engineer

Spent Tuesday afternoon writing three files: which controller reaches which infrastructure (controllers.yaml), which alert maps to which remediation and under what limits (actions.yaml), and who's allowed to trigger, override, or approve what (auth.yaml). Isn't on call tonight. Won't be woken up either way.

The on-call engineer

Carries the pager this week. Phone on the nightstand, ringer on. Has no idea, going to sleep, which of tonight's alerts will need them and which will already be handled by the time they check Slack in the morning.

The shift

23:47 → 04:03
23:47

A disk fills uplog-shipper-04 · bare metal

/var/log crosses 91% on a log-shipping box. Grafana's alert fires into Alertmanager, whose webhook receiver relays it as a call to Auto-Healer:

POST /webhook { "event_type": "cleanup_disk", "parameters": { "path": "/var/log" }, "controller_override": "log-shipper-04" }

Auto-Healer resolves cleanup_disk to its Ansible controller, SSHes in, runs the cleanup script, and writes the result to the audit chain. Four seconds, start to finish.

auto-resolved ansible · ssh
00:32

A service won't stay upweb-02 · VM fleet

An nginx health check fails on web-02. restart_service runs, clean. Six minutes later, the same check fails again — Auto-Healer restarts it a second time, because nothing in actions.yaml puts a cooldown on this action. At 00:41 it fires a third time, and this call is rejected outright — 429, before the action logic ever runs — because the platform engineer set a per-action rate limit on exactly this alert.

The on-call engineer sleeps through all three. What they find in the morning isn't a mystery — it's three timestamped attempts and a rate-limit block, which reads unambiguously as this is flapping, not a fluke.

rate limit → 429 ansible · ssh
02:15

A Deployment crash-loopspayment-service · OpenShift

Restart counts climb on payment-service. Auto-Healer calls a kube_action directly against the Kubernetes API — no bastion, no SSH — using an in-cluster ServiceAccount scoped to exactly this:

POST /webhook { "event_type": "restart_deployment_kubeapi", "parameters": { "deployment": "payment-service", "namespace": "payments" } }

The rollout restarts clean. This action carries a five-minute cooldown keyed on the deployment name — if it crash-loops again inside that window, Auto-Healer won't restart it a second time; it writes blocked-by-cooldown and leaves the real bug for a human, rather than papering over it with a tighter and tighter restart loop.

auto-resolved kubeapi · direct, no ssh 5 min cooldown
04:03

A node goes unhealthyworker-12 · OpenShift DaemonSet

This one's different — draining a node evicts real, running workloads. The platform engineer marked this specific alert approval_required, so Auto-Healer doesn't drain anything; it queues the request and hands back an approval_id, 200 pending.

The team's on-call bot — a thin wrapper around POST /approvals/{"{"}id{"}"}/approve — posts the pending request to Slack. The on-call engineer reads it, taps approve from their phone, and then Auto-Healer cordons the node, skips the DaemonSet's own pods (they're supposed to be everywhere), and evicts the rest respecting PodDisruptionBudgets.

Two minutes of attention, from bed, instead of a laptop and a terminal at 4am.

approval required kubeapi · drain_node resolved · 1 tap

What actually happens to that POST

The request's path

Every one of those four calls takes the same route. Most of what distinguishes tonight's incidents is which gate stopped the request, or waved it through.

The guardrails, briefly

Why on-call can trust it

Rate limiting

Caps how often one caller — or one specific action, across every caller — can hit /webhook per minute. An alert storm throttles instead of hammering the fleet.

Cooldowns

A per-action, optionally per-target timer. A real bug that keeps tripping the same alert gets one remediation attempt, then silence — not an escalating restart loop.

RBAC + per-key scoping

Roles gate who can override a controller, approve a request, or trigger anything at all. A single API key — say, the one Alertmanager uses — can be scoped to only the specific actions and controllers it should ever call.

Approval workflow

Any action can require a second, different set of human eyes before it runs — never the requester's own. Draining a node waits for a tap; cleaning a disk doesn't have to.

Dry-run

Every action can be simulated end-to-end — controller resolved, parameters templated, nothing executed. How a new automation gets trusted before it's ever allowed to touch anything live.

Tamper-evident audit trail

Every attempt — resolved, blocked, or escalated — is written to a hash-chained log. Editing or deleting an entry after the fact breaks the chain in a way a verify check catches.

Wiring it to Grafana

What the platform engineer actually built

Alertmanager's webhook receiver posts its own fixed envelope — alert labels and annotations, not an arbitrary JSON body. So the honest version of this story has one small piece the diagram above doesn't show: a thin relay (a few dozen lines, wherever the team already runs webhook glue) that reads an alert's labels and calls Auto-Healer with the shape it actually expects.

alert labels → relay → Auto-Healer
{"{"} "alertname": "DiskAlmostFull", "instance": "log-shipper-04" {"}"} ↓ relay maps alert → action POST /webhook { "event_type": "cleanup_disk", "controller_override": "log-shipper-04", "parameters": { "path": "/var/log" } }

Everything past that POST — the guardrails, the dispatch, the audit entry — is Auto-Healer's job, not the relay's. The relay only needs to know one thing: which alert means which action.

06:15 — handoff

What the next shift sees

The morning platform engineer doesn't ask the on-call engineer what happened overnight — they read it. GET /audit shows four real attempts and one rejected one, each with who triggered it, what ran, and what came back. Before touching any of it, they check the chain itself hasn't been:

GET /audit/verify {"{"} "ok": true, "entries_checked": 14, "first_broken_line": null {"}"}

The web-02 flap becomes a ticket, not a war story — the rate-limit block already did the work of noticing. The node drain shows exactly who approved it and when. Nobody has to reconstruct any of this from memory, and the on-call engineer — who is, notably, still asleep — doesn't have to be asked.

The phone on the nightstand never lit up.

That's the whole pitch — not that nothing goes wrong at night, but that most of what goes wrong doesn't need a person awake for it.
